# Управление исходным кодом

## Коммиты

Используется Conventional Commits 1.0.0: `type(scope): описание`.
`scope` необязателен: допустимо `docs: update report`. Для несовместимого
изменения используется `!` после типа/области или footer `BREAKING CHANGE:`.
Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `style`, `build`, `ci`,
`chore`, `revert`. Пример: `feat(catalog): add route listing (SGT-3)`.
Заголовок — до 100 символов, тип строчными буквами, непустое описание без точки
в конце. Английское описание начинается со строчной буквы. Тело отделяется
пустой строкой; строки тела/footer — до 100 символов, кроме URL.
Один коммит содержит одно законченное изменение. ID задачи желательно указывать
в сообщении, а ссылка на YouTrack обязательна в описании PR.

После `make setup` hook `.githooks/commit-msg` отклоняет неверное сообщение.
Его можно проверить без создания коммита:

```sh
printf 'bad message\n' > /tmp/sgt-commit-message
.githooks/commit-msg /tmp/sgt-commit-message
```

Независимая проверка в CI проверяет все коммиты диапазона push/PR, в том числе
первый коммит новой ветки. Обход локального hook не позволяет обойти CI.

## Ветвление

Используется GitHub Flow: постоянная ветка `main` и короткие ветки задач
`<тип>/SGT-<номер>-<описание>`. Это соглашение об именах внутри проекта.
Номер — положительное целое без ведущего нуля. Описание — строчные латинские
буквы и цифры, слова разделяются одним дефисом. Пробелы, `_`, вложенные `/`
и заглавные буквы в описании запрещены. Отдельная `develop` не используется.

| Префикс    | Назначение                     | Пример                            |
| ---------- | ------------------------------ | --------------------------------- |
| `feature/` | Новая функциональность         | `feature/SGT-3-route-catalog`     |
| `bugfix/`  | Исправление ошибки             | `bugfix/SGT-15-ci-checks`         |
| `docs/`    | Документация и отчёты          | `docs/SGT-15-report`              |
| `chore/`   | Инфраструктура, CI и окружение | `chore/SGT-15-workflow-standards` |

Проверка `scripts/check-branch.sh` принимает только `main` или имя по шаблону:

```regex
^(feature|bugfix|docs|chore)/SGT-[1-9][0-9]*-[a-z0-9]+(-[a-z0-9]+)*$
```

После `make setup` hook `.githooks/pre-push` проверяет имена **веток назначения**:
отправка `HEAD:неверная-ветка` также отклоняется. Удаление веток и отправка тегов
разрешены этим hook. Прямой push в `main` блокирует защита GitHub.
В CI шаг `Branch naming` выполняет ту же проверку для push, PR и ручного запуска
на ветке. Для PR используется исходная ветка `github.head_ref`, а не служебная
ветка слияния. На тегах проверка имени ветки пропускается.

Локальная проверка примеров:

```sh
sh scripts/check-branch.sh feature/SGT-3-route-catalog
sh scripts/check-branch.sh feature/routes # ошибка: нет ID SGT
npm run test:scripts
```

Локальный hook можно отключить, но ошибочное имя приведёт к неуспешной
обязательной проверке `quality` и заблокирует слияние в `main`.

## Pull request и слияние

Один PR решает одну задачу и направляется в `main`. Заголовок соответствует
Conventional Commits и будущему squash-коммиту, например
`ci(branches): enforce task branch names (SGT-15)`. Он автоматически проверяется
commitlint в CI. Изменение заголовка или описания PR повторно запускает проверку.

Шаблон `.github/pull_request_template.md` содержит разделы «Что изменено»,
«Проверка», «Связанная задача». В них указываются результат, выполненные команды
и результаты проверок, ссылка на YouTrack; для интерфейса прикладывается снимок
экрана. Полнота описания проверяется при самопроверке PR, автоматически
проверяется только формат заголовка.

1. Создать ветку от актуальной `main`.
2. Внести изменения и выполнить `make check` с тестовой БД.
3. Отправить ветку и открыть PR со ссылкой на YouTrack.
4. Дождаться обязательной проверки `quality`, устранить замечания.
5. Выполнить squash merge с сообщением Conventional Commits.
6. Удалить завершённую рабочую ветку после слияния при необходимости.

Защита `main` требует PR и актуальную успешную проверку `quality`; принудительные
push и удаление запрещены, правило распространяется на администратора.
Требуется линейная история и закрытие обсуждений перед слиянием. Обязательное одобрение
другого участника не включено: проект выполняет один студент. Самопроверка PR
обязательна, но не выдаётся за независимое ревью.

В начально пустом репозитории первый служебный коммит создаётся в `main`, после
чего включается защита. Дальнейшие изменения проходят через PR.

## Качество кода

Формат Go задаётся `gofmt`, анализ — `go vet`. Для JS/JSX используются ESLint
и Prettier с настройками репозитория; ошибки и предупреждения ESLint запрещены.
`make lint` проверяет эти правила локально и в CI без автоматического изменения
файлов. Модульные и интеграционные тесты, покрытие, метрики и сборка выполняются
через `make check` с отдельной тестовой PostgreSQL. Проверка текста комментариев
не настроена. Пороги покрытия и правила замеров описаны в [метриках](quality.md).

## Релиз

После слияния успешного PR получить актуальную `main`, поставить аннотированный
тег `vMAJOR.MINOR.PATCH` и отправить его. Нумерация основана на SemVer:
исправления увеличивают PATCH, совместимые функции — MINOR, несовместимые
изменения публичного API — MAJOR; серия `0.x` относится к начальной разработке.
Уже выпущенный учебный пример:

```sh
git switch main
git pull --ff-only
git tag -a v0.1.1 -m 'SGT lab 5 infrastructure preview'
git push origin v0.1.1
```

Workflow повторно запускает линтеры, тесты, метрики и сборку на теге. Затем
автоматически создаёт предварительный GitHub Release и добавляет проверенный
архив. При неуспешных проверках job публикации не запускается. Следующий тег
должен иметь новый номер версии; уже опубликованные теги не передвигаются.

## Связь с YouTrack

[Проект SGT](https://vasmaae.youtrack.cloud/issues/SGT) остаётся источником задач,
оценок и графика. Для ЛР5 инфраструктура относится к SGT-15. Минимальный каталог
связан с SGT-3 и SGT-4, но не означает завершение всех функций соответствующей
итерации. Отсутствующие функции не переводятся в Done.

Начало работы: In Progress. После подготовки результата и доказательств:
In Review. Done — после проверки всех критериев задачи. Фактическое время
указывает исполнитель; автоматически рассчитанные часы не записываются.

## Проверка учебных отчётов

Отчёт лабораторной работы сначала готовится локально и передаётся пользователю
на проверку. Включать конкретную версию в коммит или PR и публиковать её на
GitHub можно только после явного одобрения этой версии пользователем.

Основания: [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/),
[GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow),
[SemVer 2.0.0](https://semver.org/).
